## 2. AGENT-01 引合書読み取りエージェント

### Part 1: エージェントの定義（基本設計）

> プロダクト定義レビュー（`/design-product-check`）の対象。

#### ミッション

営業事務（中村）が、引合書類一式を読んで品目リストに手で写している仕事のうち、**「読んで写す」部分を代行する**。確認と確定は人が行う（① 前提・制約1）。エージェントの成果物は**確定前の品目リスト案**であり、品目リストそのものではない。

**対応機能(②)**: FUNC-02（引合内容の抽出）、FUNC-07（読み取り不可の判定と引き渡し）。FUNC-03（処理状況の表示）には、実行の進み具合を情報源として渡す。

**エージェントに任せること／任せないこと**

書類の書式が顧客ごとに違い、決め打ちのコードでは対応できない部分だけを LLM の判断に任せる。毎回同じ手順で書ける部分は通常のコードで作る。

| エージェント（LLM の判断）に任せる | 通常のコードで作る |
|---|---|
| 明細がどこにあるかを見つける（シート・表・ページ・段落・本文の範囲） | 形式判定（拡張子で決まる。FUNC-01） |
| 列や項目の意味を決める（「型式」「品番」→ 型番、など顧客ごとに違う見出し） | ファイルの中身を位置つきで取り出す（openpyxl / python-docx / PDF ライブラリ） |
| 小計・合計・注記の行を明細から外す | 読み取り元の位置に、その値が本当にあるかの照合 |
| 数量と単位を分ける、納期を (a)(b)(c) の値域に当てはめる | 数量・納期・必須5項目の形式の検査 |
| 複数ファイルの内容を1つの品目リスト案に束ねる | 完了条件の判定（`check_completion`） |
| 読み違いの疑いがある値に「確信が低い」を付ける。記載がない必須項目を「要確認」にする | 確認・除外・確定・Excel 出力（FUNC-04〜06。人の操作） |
| 明細のないファイル、判読できないファイルを見分ける | 残り時間の目安の計算、状態の表示 |

#### インプット

| 項目 | 内容 |
|------|------|
| 起動トリガー | ユーザー操作。SCR-03 で「投入する」を押し、案件が受付済みになったとき、service 層が `jobs.start_agent_job()` でバックグラウンド実行を始める（POST → 202 + run_id）。SCR-10 の「再実行」（理由がタイムアウト／最大ターン数超過のときだけ、1回まで。② FUNC-07）でも同じ経路で起動する |
| 入力データ | 案件ID（サーバー側で固定する）／投入ファイル 1〜10件（.xlsx / .pdf / .docx、合計 50MB 以内）と、任意のメール本文テキスト（② FUNC-01）／DB から参照: 投入ファイルの一覧と原本 |
| コンテキスト方針 | **渡すもの**: システムプロンプト（ミッション、必須5項目と任意の備考、納期の値域 (a)(b)(c)、「未確認・確信が低い・要確認」の定義、確信が低いと判断する手がかり H1〜H4、小計・合計・注記の扱い、完了条件）／ファイル一覧（名前・形式・サイズ）／ツールで読んだ中身（位置つきで、少しずつ） **渡さないもの**: 過去の案件の抽出結果や顧客ごとの書式情報（書式の事前登録に頼らない。② Out of Scope・KPI4）／他の案件のデータ／原本の全文を一度に（ページングで読む）／ユーザー情報・API キー・内部設定 |

**確信が低いと判断する手がかり**（KPI8 の達成条件に直結するため、ここで固定する）

| 記号 | 名前 | 手がかり | 例 |
|------|------|---------|-----|
| H1 | ファイル間不一致 | 複数のファイルで、同じ品目の値が違う | Excel と PDF で、同じ型番の数量が違う |
| H2 | 列内の形式ずれ | 同じ列の他の行と形式が違う（英数字の型番に全角が混ざる、O と 0 の混在、余分な空白など） | 他の行が `BRG-6205-2RS` の形で並ぶ中、1行だけ `BRG-62O5-2RS`（数字の 0 が英字の O） |
| H3 | 単位数量の不自然 | 単位と数量の組み合わせが不自然、または数量が他の行と桁違い | 六角穴付きボルトの単位が「m」 |
| H4 | 正規化の非一意 | **正規化したが、解釈が一意に定まらなかった**（この場合に限る） | 「月末」が月内の範囲か特定日かを決めきれない、単位の候補が複数ある |

- 記号は納期の値域 (a)(b)(c) と混ざらないよう H1〜H4 とし、記号だけでは意味が分からなくならないよう名前を添える
- Build では H1〜H4 を**列挙型の値**として定義し、確信が低い理由として値に付ける
- 1つの値に複数の手がかりが立つ場合は、**すべて記録する**（評価のときに、どの手がかりが効いたかを分かるようにするため）

- 解釈が一意に定まる正規化（「10月末」→ 納期の値域 (b) 月内の範囲、「3箱(1箱50本)」→ 数量 3・単位 箱）だけでは確信を下げない。正規化した値は必ず原本の文字列と違うため、それだけで下げると正規化した行がすべて「確信が低い」になってしまう
- 読み取り元の照合で一致しないことは、手がかりにしない。照合の不一致は完了条件④で「未完了」として扱い、確信度とは二重に定義しない

確信が低い値には、どの手がかり（H1〜H4、1つ以上）で判断したかを記録する（SCR-06 で中村が理由を見られるように）。

**原文と値**: 値ごとに、原本に書かれていたとおりの文字列（原文）と、正規化したあとの値の両方を持つ。読み取り元の照合は**原文**で行う（正規化した値は原本の文字列と一致しないため）。

**行の分類**は値の状態から決める。要確認の値が1つでもあれば「要確認」、なければ確信が低い値が1つでもあれば「確信が低い」、どちらもなければ「確信が高い」。

#### 完了条件・停止条件

| 種別 | 条件 | 判定方法 |
|------|------|---------|
| 成功（完了） | 次の①〜⑤をすべて満たす。① 投入した全ファイルの状態が「読み取り済み（明細あり）」「読み取り済み（明細なし）」「読み取り不可（判読不能）」のいずれかになっていて、読み取り済みが1件以上ある ② 品目リスト案が1行以上ある ③ 全行の必須5項目（品目名・型番・数量・単位・納期）が、値か「要確認」で埋まっている（空欄0） ④ 抽出したすべての値に読み取り元（ファイルと位置）があり、その位置に原文があるかの照合で不一致が0件 ⑤ すべての値に確信度（高／低）が付き、確信が低い値には手がかり（H1〜H4）が1つ以上付き、数量は数値、納期は (a)(b)(c) のいずれか | エージェントが最後に `check_completion` を呼び、決まった手順のチェック関数が①〜⑤すべて OK を返したときだけ完了とする（LLM の自己申告では完了にしない）。案件の状態を「確認待ち」にし、トレースの `stop_reason` は `completed` |
| 失敗（中断） | (1) 投入した全ファイルが読み取り不可（判読不能） (2) 読み取れたファイルの明細が合計0行（明細を含まない書類だけが投入された） | `check_completion` がファイルの状態と行数から判定し、案件を「読み取り不可」にする。理由は (1) 判読不能 (2) 明細なし。`stop_reason` は `failed` |
| 強制停止 | 最大ターン数 30 ／ タイムアウト（無応答 60秒 < 内側 300秒 < 外側 360秒） | 最大ターン数は SDK の `max_turns` で数え、結果の `stop_reason`（`max_turns`）で判別する。無応答と内側は `runner.py` が計時する（`inactivity_timeout` / `inner_timeout`）。外側は `jobs.py` が計時する（`outer_timeout`）。いずれも案件を「読み取り不可」にし、それまでに保存した案と読めた範囲は破棄しない |

`check_completion` が NG（①〜⑤のどれかを満たさない）を返したときは、エージェントは不足を直して呼び直す。直せないまま続けた場合は、最大ターン数かタイムアウトで止まる。

**停止理由と、② FUNC-07・③ SCR-10 の理由の対応**

| トレースの `stop_reason` | 案件の状態 | 画面に出す理由（② FUNC-07） | 再実行（② FUNC-07） |
|------------------------|----------|--------------------------|------------------|
| `completed` | 確認待ち | —（一部のファイルが判読不能なら、そのファイルだけ SCR-05 で示す） | — |
| `failed`（全ファイル判読不能） | 読み取り不可 | 判読不能 | できない |
| `failed`（明細が0行） | 読み取り不可 | 明細なし | できない |
| `max_turns` | 読み取り不可 | 最大ターン数超過 | 1回だけできる |
| `inactivity_timeout` / `inner_timeout` / `outer_timeout` | 読み取り不可 | タイムアウト | 1回だけできる |

**実行設定**（`backend/app/agent/definition.py` に写す値。片方だけ変えない）

| 項目 | 値 | 理由 |
|------|-----|------|
| モデル | `claude-sonnet-5` | 入力 $2 ／ 出力 $10（100万トークンあたり）。月の支出上限は $50 で、評価は M6 の1回で終わらず開発中に何十回も動かすため、Opus 5（見積もり $16〜60）では上限に当たるおそれがある。判断の質が足りない場合に、プロンプトとツール設計で補う過程そのものを「精度向上の工夫」として残す |
| 最大ターン数（`MAX_TURNS`） | 30 | ファイル2つの典型的な案件で約10ターン、上限の10ファイルで約25ターンと見積もり、余裕を持たせた |
| 無応答（`INACTIVITY_TIMEOUT_S`） | 60秒 | メッセージが60秒来なければハングとみなす |
| 内側（`INNER_TIMEOUT_S`） | 300秒 | エージェント実行全体の上限。下の「02 の性能要件との関係」を参照 |
| 外側（`OUTER_TIMEOUT_S`） | 360秒 | `jobs.py` の最後の砦。内側より必ず長くする |

**モデルを上げる判断基準**: まず `claude-sonnet-5` で評価する。KPI4（8件を1件10分以内・見逃し0）または KPI8（仕込んだ誤りが確信が低いと示される）が未達で、原因が列の意味づけや確信度の判断の質にあると切り分けられた場合に限り、`claude-opus-5` に上げる。モデルを上げる前に、プロンプトとツールの出力形式の改善を先に試す。上げるときは、この表を先に変えてから `definition.py` を変える。

**タイムアウトと 02 の性能要件との関係**

**タイムアウトは異常時に打ち切るための上限であり、目標値ではない。02 の性能受入基準（平均12行の案件を180秒以内）は典型的な案件に対する目標であって、外側タイムアウト360秒は 10ファイル・合計50MB の最大構成でも打ち切れるようにした上限である。**

02 の非機能要件（性能）は「平均12行の引合書1件について、投入から確認待ちになるまで3分以内」を受入基準にしている。内側・外側のタイムアウトは、それを大きく超えたときに打ち切るために置く。

| 経過時間 | 意味 | 画面（③） | 評価上の扱い |
|---------|------|----------|------------|
| 0〜180秒 | 目標どおり | SCR-04 に残り時間の目安 | 性能の受入基準を満たす |
| 180〜300秒 | 目標は超えたが処理は続く（10ファイル・30行など大きい案件を想定） | SCR-04 に「目安の時間を過ぎていますが、処理を続けています」 | 完了すれば成功。ただし平均12行の案件でここに入るなら性能の受入基準は未達 |
| 300秒（内側） | 打ち切り | SCR-10「読み取り不可 — タイムアウト」。再実行1回（② FUNC-07） | `inner_timeout`。停止条件どおりに止まれば停止条件の評価は Pass |
| メッセージ間60秒（無応答） | ハングとみなして打ち切り | 同上 | `inactivity_timeout` |
| 360秒（外側） | 内側が効かなかった異常 | 同上 | `outer_timeout`。発火したら内側の不具合として調査する（Slice 0-7 のルール） |

大小関係は **無応答 60秒 < 目標 180秒 < 内側 300秒 < 外側 360秒** とする。目標と内側の間の120秒が、大きい案件のための余裕になる。

**出力形式**: DB（→ ④）に保存する構造化データ。Excel は出力しない（Excel は人が確定したあとに FUNC-06 が作る）。

| 出力 | 中身 |
|------|------|
| 品目リスト案 | 案件ごとの品目行。行番号・行の分類・その行を読んだファイル、値ごとに {原文、正規化した値、状態（抽出／要確認）、確信度（高／低）、確信が低い手がかり（H1〜H4 の列挙値。複数可）、読み取り元（ファイルと位置）}。納期は {種別 (a)(b)(c)、開始日、終了日} |
| 投入ファイルの状態 | ファイルごとに 読み取り済み（明細あり・行数）／読み取り済み（明細なし）／読み取り不可（判読不能）と、どこまで読めたか |
| 実行記録 | run_id・案件ID・開始と終了の時刻・ターン数・`stop_reason`・再実行の回数 |
| トレース | `backend/traces/{run_id}.jsonl`（IPO 拡張表と同じ形。原本の全文は残さない） |

#### ユーザーから見た体験

- **実行中の見え方**: ストリーミングはせず、ポーリングで進み具合を見せる（Slice 0-7 の型: POST → 202 + run_id → GET で取得）。SCR-04 に段階（受付済み → 読み取り中 → 確認待ち／読み取り不可）と残り時間の目安、SCR-02 の一覧に状況と補足を出す。進み具合はトレースの末尾から取る（読み終えたファイルの数など）。中村は待たずに別の案件へ移れる（① ジャーニー ステップ2）
- **中間承認**: **実行中はなし**。エージェントが書き込めるのは下書き（品目リスト案）と状態の記録だけで、外に出る操作や取り返しのつかない操作を持たないため。人の承認は実行のあとに置く（SCR-05 で確認し、SCR-09 で確定する。① 前提・制約1）
- **対応画面(③)**: SCR-03（起動）／SCR-04・SCR-02（進み具合）／SCR-05・SCR-06（成果物の確認。読み取り元と確信が低い手がかりを見せる）／SCR-10（失敗・再実行）

### Part 2: エージェントの実現（詳細設計）

> 実装設計レビュー（`/design-implementation-check`）の対象。

#### ツール一覧

完了条件から逆算した。人がこの仕事をするなら「投入されたファイルを確かめる → 開いて読む → 品目リストに書く → 見直す → 読めないもの・明細のないものを報告する → 終わったか確かめる」ので、その6つをツールにする。

| ツール名 | 目的 | 入力 | 出力 | 副作用 | 必要なAPI/テーブル(→④⑤) |
|---------|------|------|------|--------|------------------------|
| `list_input_files` | 案件に投入されたファイルを知る | なし（案件IDはサーバー側で注入） | ファイルごとの ID・名前・形式・サイズ、メール本文の有無 | read | 案件、投入ファイル |
| `read_file_content` | ファイルの中身を、読み取り元として示せる位置つきで読む | ファイルID、読む範囲（シート・ページ・段落・行の範囲。省略時は先頭から） | 位置つきの中身（Excel はセル番地、PDF はページと行、Word は表の番号・行・列または段落番号、メール本文は行番号）、続きがあるか、文字として読める情報があるか | read | 投入ファイル（原本の保存場所）。1回に返す量に上限を設ける（値は Build で決める） |
| `save_item_rows` | 品目リスト案を下書きとして保存する。保存のたびに形式を検査する | 品目行の一覧（原文・正規化した値・状態・確信度・手がかり・読み取り元） | 保存した行数と、検査で見つかった誤りの一覧（必須5項目の空欄、数値でない数量、値域の外の納期、読み取り元のない値、案件にないファイルを指す読み取り元） | write（下書きだけ。案件の品目リスト案を丸ごと置き換える） | 品目行、品目の値 |
| `verify_sources` | 保存した値の原文が、読み取り元の位置に本当にあるかを照合する | なし（保存済みの案をすべて照合） | 不一致の一覧（原文・読み取り元・その位置に実際にある文字列） | read | 品目の値、投入ファイル |
| `set_file_status` | 明細のないファイル、判読できないファイルを記録する | ファイルID、状態（明細なし／判読不能）、どこまで読めたか | 記録した状態 | write（ファイルの状態だけ） | 投入ファイル |
| `check_completion` | 完了条件①〜⑤と失敗条件を判定し、案件の状態を決める | なし | 判定結果（完了／失敗: 判読不能／失敗: 明細なし／未達: どの条件を満たしていないか） | write（完了・失敗のときだけ案件の状態を変える） | 案件、実行記録 |

「読み取り済み（明細あり）」は、`save_item_rows` で保存した行の読み取り元から自動で決まる。エージェントが明示するのは「明細なし」「判読不能」だけ。

> 副作用 = read（参照のみ）/ write（作成・更新・削除・外部送信）。write ツールはガードレールと突き合わせる。
> 最終列は 04-db / 05-api-ipo の設計課題リスト。ここに書いた要求が後続の設計で実現される。

**ツール以外に 04・05 で必要になるもの**（エージェントの起動・進捗・結果）

| 要求 | 内容 | 対応画面 |
|------|------|---------|
| エージェントの起動 API | 案件を指定して実行を始め、202 と run_id をすぐ返す。再実行も同じ API（再実行の回数を検査する） | SCR-03・SCR-10 |
| 進捗取得 API | run_id を指定して、段階・読み終えたファイルの数・残り時間の目安・停止理由を返す（ポーリング） | SCR-04・SCR-02 |
| 結果取得 API | 案件の品目リスト案・投入ファイルの状態を返す | SCR-05・SCR-06・SCR-10 |
| 実行記録テーブル | run_id・案件ID・開始と終了の時刻・ターン数・`stop_reason`・再実行の回数 | — |
| 原本の保存場所 | 投入ファイルの原本をローカルに置き、保持期間（② 非機能）で削除できるようにする | SCR-10（原本ダウンロード） |

#### サブエージェント構成

**単体**（オーケストレーター1体のみ）。分割しない理由:

- **責務が独立しない**。形式ごとの差（Excel・PDF・Word・メール本文）は `read_file_content` の中（コード側）で吸収されるので、形式ごとにエージェントを分ける理由がない
- **コンテキストは1体でも制御できる**。`read_file_content` が位置つきで少しずつ返すので、最大10ファイルでも1体のコンテキストに収まる
- **並列性は変わらない**。LLM のループは逐次なので、1体でも複数体でも速さは変わらない
- **分けると費用が上がる**。親子のトレースとターン数が増え、そのぶん費用が上がる

見直す条件: 評価で、10ファイルの案件がコンテキストの上限や内側タイムアウトに当たるなら、「1ファイルを読んで候補行を返す」read 系だけのサブエージェントに読みを分けることを検討する（そのときはこの節と下のフロー表を先に更新する）。

> サブエージェントの呼び出しは、オーケストレーターから見れば**ツール呼び出しと同型**
> （＝コンテキストを隔離した大きなツール）。エージェントフロー（下表）では「ツール実行」の列に
> サブエージェント呼び出しとして書き、実行トレースにも親子関係付きで記録される。

#### エージェントフロー（IPO拡張）

> 正常系の典型的な1実行（見積依頼.xlsx ＋ 仕様書.pdf）を粗く追うスケッチ。ツールの呼び出し順は固定しない。

| ステップ | Input | 判断(Process) | ツール実行 | 観察/Output |
|---------|-------|--------------|-----------|------------|
| 1 | 案件ID（注入済み）・システムプロンプト | 何が投入されたかを知る | `list_input_files` | 2件（見積依頼.xlsx、仕様書.pdf） |
| 2 | ファイル一覧 | 明細がありそうな Excel から読む | `read_file_content`（見積依頼.xlsx） | シート「明細」の9行目に見出し、10〜22行目に明細と小計行 |
| 3 | Excel の中身 | 見出し「型式」を型番に、「希望納期」を納期に対応づける。小計行を外す。「3箱(1箱50本)」を数量 3・単位 箱に分け、「10月末」を (b) 月内の範囲にする（解釈が一意なので確信は下げない）。1行だけ `BRG-62O5-2RS` と文字種の違う型番を、原文のまま確信が低いにする（H2 列内の形式ずれ） | —（判断のみ） | 11行の候補 |
| 4 | 候補 | 仕様書に明細の追加や補足があるかを確かめる | `read_file_content`（仕様書.pdf） | p.2 に明細表。1品目の追加と、Oリングの材質 NBR |
| 5 | 両ファイルの内容 | PDF の追加品目を行にし、材質を備考に入れる。Excel と同じ品目は突き合わせずに別の行とし、数量が食い違う行は確信が低い（H1 ファイル間不一致） | `save_item_rows`（13行） | 検査の誤り1件: 1行の数量の原文が「2OO」で、値が数値でない |
| 6 | 検査結果 | 原文は「2OO」のまま残し、値を 200 と解釈して確信が低いにする（H2 列内の形式ずれ。直すかどうかは中村が SCR-07 で決める） | `save_item_rows`（13行） | 検査 OK |
| 7 | 保存済みの案 | 読み取り元が正しいかを照合する | `verify_sources` | 不一致1件（読み取り元の行が1つずれている） |
| 8 | 不一致 | 該当箇所を読み直して読み取り元を直す | `read_file_content`（見積依頼.xlsx の該当範囲）→ `save_item_rows` | 保存 OK |
| 9 | 直した案 | 完了条件を充足したか判定 | `check_completion` → -（終了） | ①〜⑤すべて OK。案件は「確認待ち」、`stop_reason=completed` |
| 異常 | 全ファイルで文字が取れない | 判読不能と判断する | `set_file_status`（判読不能）→ `check_completion` | 失敗: 判読不能。案件は「読み取り不可」、`stop_reason=failed` |
| 異常 | 実行が300秒を超える | —（runner が打ち切る） | — | `inner_timeout` を記録。案件は「読み取り不可（タイムアウト）」、保存済みの案と読めた範囲は残す |

検算: 呼んだツールはすべてツール一覧にある。最終行は `check_completion` で判定できる。読む順番・どこを明細とみなすか・検査や照合の結果にどう対処するかが入力ごとに変わるため、決め打ちのコードではなくエージェントで作る理由がある。

#### ガードレール

- **してはいけない操作**（お願いではなく、仕組みで止める）:

| してはいけない操作 | 止め方 |
|------------------|--------|
| 品目リストの確定・Excel 出力・行やファイルの除外 | そのツールを与えない（`allowed_tools` は上の6つだけ） |
| 原本の変更・削除 | 原本に書き込むツールがない。`read_file_content` は読み取り専用 |
| 引合書にない値を推測で埋める | 要確認以外の値には読み取り元を必須にし、`save_item_rows` の検査・`verify_sources`・`check_completion` ④ で機械的に弾く |
| 組み込みツール（Bash・Read・Write・Edit・Glob・Grep・WebFetch・WebSearch・Task など）を使う | `disallowed_tools` で使わせない |
| 他の案件のデータに触れる | 案件IDはサーバー側でツールに注入し、LLM の引数では受け取らない。PreToolUse hook で、ファイルIDがその案件のものかを検査する |
| 外部へ送信する | ネットワークに出るツールがない |
| 条件を満たさずに案件を「確認待ち」にする | 案件の状態を変えられるのは `check_completion` だけで、完了条件①〜⑤を満たしたときだけ変える |
| トレースに原本の全文や個人情報を残す | `read_file_content` の観察は、トレースには要約（ファイル名・範囲・行数）だけを記録する |

- **人間の承認が必要な操作**: 確定（FUNC-06）、行の除外（FUNC-05）、読み取れなかったファイルの除外（FUNC-07）。いずれもエージェントのツールには含めず、人が SCR-05・SCR-09 で操作したときだけ実行される。再実行も人が SCR-10 で押したときだけ始まる
- **ツール権限**（方針は ② 非機能要件・セキュリティ）: エージェントを起動できるのは営業事務ロール（Scope 1 の唯一のロール）。ツールはすべて、起動された案件の中だけで動く

| ツール名 | 必要な権限 | 備考 |
|---------|-----------|------|
| `list_input_files` | 実行中の案件の読み取り | 他の案件は見えない |
| `read_file_content` | 実行中の案件の原本の読み取り | 読み取り専用。1回に返す量に上限 |
| `save_item_rows` | 実行中の案件の品目リスト案の書き込み | 下書きだけ。確定済みの案件には書けない |
| `verify_sources` | 実行中の案件の読み取り | 照合のみ |
| `set_file_status` | 実行中の案件の投入ファイルの状態の書き込み | 明細なし／判読不能だけを書ける |
| `check_completion` | 実行中の案件の状態の書き込み | 確認待ち・読み取り不可にだけ変えられる |

#### 評価シナリオ

> 入力はすべて自作のダミー書類（実在の取引先の書類は使わない）。`backend/tests/fixtures/` に置いて再評価できるようにする。

**KPI8 のテスト書類の設計要件**（手がかりを H1〜H4 に決めたので、仕込む誤りは H1〜H3 で見つけられる形にする。そうでなければテストが成立しない）

| 仕込む誤り | 捕まえる手がかり | 仕込み方 |
|-----------|---------------|---------|
| 型番の桁違い | H2 列内の形式ずれ | 他の行が `BRG-6205-2RS` の形で並ぶ中、1行だけ `BRG-62O5-2RS`（数字の 0 を英字の O に）。同じ列の他の行と文字種が違う |
| 単位の取り違え | H3 単位数量の不自然 | 六角穴付きボルトの単位を「m」にする。単位と品目の組み合わせが不自然 |
| （余裕があれば）ファイル間の食い違い | H1 ファイル間不一致 | Excel と PDF で、同じ型番の数量を違えておく |
