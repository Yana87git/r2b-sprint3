## 2. 各機能の要件

### FUNC-01 引合書の投入と形式判定

- **概要**: 1件の引合につき1つ以上のファイル（および／またはメール本文）を受け取り、それぞれを Excel / PDF / Word / メール本文のどれとして読むかを判定して受け付ける
- **事前条件**: 営業担当から転送された引合メールを、営業事務が手元に持っている
- **正常フロー**:
  1. 営業事務がファイルを投入する（メール本文の場合は本文テキストを渡す）
  2. 形式を判定し、「Excel形式として受け付けました」のように何として読むかを表示する。複数のファイルをまとめて投入でき、ファイルごとに判定結果を表示する
  3. 受付済みの状態にして、抽出（FUNC-02）を開始する
- **例外・バリデーション**:
  - 受け付けるファイル形式は .xlsx、.pdf、.docx の3つ。メール本文はファイルではなく本文テキストとして受け取る
  - 対応しない拡張子は受け付けず、その場で理由を表示する
  - ファイルが破損して開けない場合は「読み取り不可」として FUNC-07 へ回す
  - サイズ上限（1ファイルあたり 20MB）を超える場合は受け付けない
  - 11件目の入力、または合計50MB を超える投入は受け付けない
- **受入基準**:
  - Excel添付・PDF添付・Word添付・メール本文の4形式それぞれで、投入時に判定結果が表示される
  - Excel と PDF を1件の引合として同時に投入でき、両方の判定結果が表示される
  - 次の5つがそれぞれ拒否され、理由が表示される
    - 対応しない拡張子のファイル
    - 20MB を超えるファイル
    - 破損して開けないファイル（この場合は FUNC-07 の「読み取り不可」へ回る）
    - 11件目の入力
    - 合計50MB を超える投入

### FUNC-02 引合内容の抽出

- **概要**: 投入されたすべての入力（ファイルとメール本文）から 品目名・型番・数量・単位・納期・備考 を行単位で抽出し、1つの品目リストに束ねる。各値の読み取り元には、どの入力から読んだかを含める。確信度も併せて記録する
- **備考**: この機能はエージェントが実現する（`agent.md` の AGENT-01）
- **事前条件**: FUNC-01 で受け付けが完了している
- **正常フロー**:
  1. 引合書を読み、明細の範囲を特定する
  2. 行ごとに 品目名・型番・数量・単位・納期・備考 を抽出する
  3. 各値について読み取り元を記録する。読み取り元は、ファイル名と場所で表す。形式ごとの表記は次のとおり
     - Excel … `見積依頼.xlsx 明細!C12`
     - PDF … `仕様書.pdf p.2`
     - Word … `依頼書.docx 表2 3行目2列目` ／ `依頼書.docx 12段落目`
     - メール本文 … `本文 14行目`
  4. 各値の確信度を判定し、読み違いの疑いがある値に「確信が低い」印を付ける
  5. 引合書に記載がない必須5項目（品目名・型番・数量・単位・納期）は「要確認」とする（空欄にしない）。任意項目の備考は、記載がなければ空欄のままとし、要確認にしない
- **例外・バリデーション**:
  - 小計行・合計行・注記行を明細として拾わない
  - 数量と単位が同じセルに書かれている場合は分離する（例「3箱(1箱50本)」）
  - 納期の表記ゆれ（「10月20日」「10/20」「10月末」「未定」）を、次の3つの値域のいずれかに正規化する。FUNC-05 の検査もこの値域に従う
    - (a) 確定日付 … 例 2026-10-20
    - (b) 月内の範囲 … 例「10月末」→ 2026-10-21〜2026-10-31 として保持し、範囲であることを明示する
    - (c) 要確認 … 「未定」や記載なしはここに入る
  - 判読できない場合は FUNC-07 へ回す
  - 最大ターン数・タイムアウトに達した場合は打ち切って状態を残し、「読み取り不可」として FUNC-07 へ回す
- **受入基準**:
  - 型番の桁違いと単位の取り違えを仕込んだ引合書で、該当行が「確信が低い」として示される（KPI8）。誤りの仕込み方は `agent.md` の「KPI8 のテスト書類の設計要件」に従う。手がかり H1〜H3 で見つけられる形に仕込む（型番は列内の文字種を変える、単位は品目との組み合わせを不自然にする、など）
  - 納期または数量が欠けている引合書10件すべてで、確定前に欠落が提示される（KPI3）
  - 読み取り元 (1) 網羅性: 抽出したすべての値に読み取り元が付いている。欠けが0件
  - 読み取り元 (2) 正しさ: 4形式（Excel添付・PDF添付・Word添付・メール本文直書き）が各2回以上現れる計8件（うち2件は複数入力の案件）を処理し、各件から無作為に5つの値を選んで読み取り元が指すファイルと場所を開き、読み取り元が指す場所に、実際にその値の原文があることを確認する。正規化を挟んだ値（「10月末」→ 月内の範囲、「3箱(1箱50本)」→ 数量3・単位箱）は、正規化後の値ではなく保持している原文と照合する。計40値すべてが一致すること（一致率100%）。KPI4 と同じ8件を使う。形式ごとの確認方法:
    - Excel … 指定されたファイルの、指定されたシートのセル番地に、原文が存在する
    - PDF … 指定されたファイルの、指定されたページに、原文が存在する
    - Word … 指定されたファイルの、指定された表の行・列、または段落番号の位置に、原文が存在する
    - メール本文 … 指定された行番号に、原文が存在する
  - 次の2つが正しく処理される
    - 小計行・合計行・注記行を明細として拾わない。単一の入力を投入した場合に、抽出される行数が、その入力の実品目数（小計行・合計行・注記行を除いた数）と一致する。複数の入力を投入した場合は、重複を突き合わせずに並べる方針のため、各入力の実品目数の合計と一致することを確認する
    - 数量と単位が同じセルに書かれている場合に分離できる（「3箱(1箱50本)」から 数量=3／単位=箱 を取り出す）

### FUNC-03 処理状況の表示

- **概要**: 引合1件の処理がいまどの段階かを表示する
- **事前条件**: FUNC-01 で受け付けが完了している
- **正常フロー**: 受付済み → 読み取り中 → 確認待ち → 確定済み の順に遷移し、各段階と残り時間の目安を表示する
- **例外・バリデーション**: 判読不能な場合、または処理が打ち切られた場合（タイムアウト・最大ターン数超過）は「読み取り不可」に遷移する。段階は5つのまま増やさない
- **受入基準**: 5段階すべてが画面上で区別でき、読み取り中は残り時間の目安が表示される

### FUNC-04 品目リスト案の確認

- **概要**: 抽出結果を3分類で表示し、読み取り元を確認しながら承認できるようにする
- **事前条件**: FUNC-02 の抽出が完了し、状態が「確認待ち」である
- **正常フロー**:
  1. 要確認の行と確信が低い行を先頭に寄せて表示する
  2. 営業事務がその行を1行ずつ確認する（要確認・確信が低い行は、まとめて確認できない）
  3. **確信が高い行を確認済みにできるのは、次のどちらかのときだけ**（個別も一括も同じ規則）:
     - (a) **その行の読み取り元を開いた**
     - (b) **抜き取りが min(3, N) に達している**（N = 確信が高く、除外していない行の数）
  4. (b) を満たすと、確信が高い行をまとめて確認済みにできる
  5. すべての行が確認済み（未確認が0）になる
- **例外・バリデーション**:
  - 未確認の行が残っている間は確定できない
  - 上の (a)(b) をどちらも満たさない確信が高い行は、**個別にも一括にも確認済みにできない**。
    画面で押せなくするだけでなく、**サーバー側が拒否する**（API を直接呼んでも同じ）
- **受入基準**:
  - 確認画面が表示されてから確定までが平均10分以内（連続10件の平均）（KPI1）
  - 4形式（Excel添付・PDF添付・Word添付・メール本文直書き）が各2回以上現れる計8件（うち2件は複数入力の案件）を、ベテラン以外の担当者が処理する。うち2件はその担当者が初めて見る書式とする。8件すべてを、ベテランに一度も聞かずに1件10分以内で確定できる。誤りの見逃しは0件（KPI4）。**KPI8 と同じ8件を使う。** 8件それぞれに既知の誤りを1件ずつ仕込み（計8件）、確定後に出力された品目リストにその誤りがそのまま残っていた件数を「見逃し」と数える。見逃し0件を合格とする。誤りの仕込み方は `agent.md` の「KPI8 のテスト書類の設計要件」に従う
  - 読み取り元を1行も開いていない状態では、確信が高い行を**個別にも一括にも**確認済みにできない（規則は上の (a)(b) の1つだけ。個別チェックだけ素通りする抜け道を作らない）
  - 抜き取りが足りないときは、**何をすればよいかが画面に出る**（「あと N 行の読み取り元を開いてください」）
  - 読み取り元 (1): 確認画面上で、読み取り元のあるすべての値から1操作で読み取り元に辿れる。要確認の値は読み取り元を持たないため、記載がないことがその場で分かる表示になる
  - 読み取り元 (2): 読み取り元の表示形式が4形式それぞれで定義どおりである（Excel = ファイル名とシート名とセル番地／PDF = ファイル名とページ番号と該当箇所／Word = ファイル名と表の位置（表番号・行・列）または段落番号／メール本文 = 行番号）

### FUNC-05 値の修正と要確認項目の提示

- **概要**: 誤って抽出された値を修正する。重複している行や、明細ではない行を除外できる。顧客に問い合わせる項目を一覧にまとめる。顧客への問い合わせは、要確認の一覧をまとめた営業事務（中村）が、現行どおりメールで手作業で送る（送信は Out of Scope）
- **事前条件**: FUNC-04 の確認画面を開いている
- **正常フロー**:
  1. 誤って抽出された値を修正する
  2. 引合書に記載がない項目は「要確認」のまま残す
  3. 要確認の項目が一覧で提示され、1通の問い合わせにまとめられる
  4. 重複している行のうち採らないほうを除外する。除外した行は品目リストに出力されず、画面上では取り消せる状態で残る
- **例外・バリデーション**:
  - 修正後の値も形式の妥当性を検査する（数量は数値、納期は FUNC-02 の値域 (a)(b)(c) のいずれか）。(b) 月内の範囲 と (c) 要確認 は弾かない
  - 除外した行の扱い
    - 未確認からは外れる（人が見て判断したため、確認済みとして数える）
    - Excel には出力しない
    - 画面上ではグレーで残し「除外」と表示する。取り消せる
- **受入基準**:
  - 要確認の項目が1画面にまとまって表示される
  - 同じ品目が2つのファイルに現れた引合で、一方を除外すると、出力された Excel にその行が含まれない。除外は画面上で取り消せる
  - 納期の値が (a) 確定日付 (b) 月内の範囲 (c) 要確認 の3つのいずれかに分類されている。(a)(b)(c) のいずれでもない値は保存できない。「10月末」は (b) として月内の範囲を持ち、「未定」は (c) になる

### FUNC-06 確定と品目リストの出力

- **概要**: 内容を承認して確定し、品目リスト（Excel）を出力する
- **事前条件**: 未確認の行が0であり、かつ読み取れなかった入力が0件であること
- **正常フロー**:
  1. 営業事務が確定を実行する
  2. 品目リスト（Excel）が出力される
  3. 要確認の行は「顧客回答待ち」と分かる形で出力に含まれる。出力された Excel は、これまでと同じ方法で購買部門に渡す（システム上での受け渡しはしない）
- **例外・バリデーション**: 未確認の行が残っている場合は確定させず「未確認の行があります」と表示する。読み取れなかった入力が残っている場合も確定させない（FUNC-07）
- **受入基準**:
  - 出力された Excel の全行に必須5項目が埋まり、引合書に記載がない項目は空欄ではなく「要確認」と明示される。区別のつかない空欄が1つでもあれば未達（KPI5）。除外した行は出力に含まれないため、検査の対象外とする
  - 未確認の行が1行でも残っている状態では確定が実行できず、「未確認の行があります」と理由が表示される。未確認0のときのみ確定できる
  - 要確認の行を含む案件を確定したとき、出力された Excel 上でその行が「顧客回答待ち」と判別できる。要確認でない行と見分けがつくこと
  - Excel と破損した PDF を1件として投入したとき、Excel の行は確認できるが、PDF の入力を除外するまで確定できない。除外すると確定できる

### FUNC-07 読み取り不可の判定と引き渡し

- **概要**: 判読できない、または処理を打ち切った引合書を「読み取り不可」とし、理由（判読不能／明細なし／タイムアウト／最大ターン数超過）を添えて人に引き渡す
- **備考**: 読み取り不可の判定はエージェントが行う（`agent.md` の AGENT-01）
- **事前条件**: FUNC-01 または FUNC-02 の途中で判読できないと判断された、読み取れた入力に明細が1行も見つからなかった、または処理が打ち切られた（タイムアウト・最大ターン数超過）
- **正常フロー**:
  1. 状態を「読み取り不可」にし、理由と、どこまで読めてどこから読めなかったかを添えて人に引き渡す。段階は1つだが、中村が見る画面では理由を区別して表示する
  2. 複数の入力のうち一部だけが読み取れなかった場合、案件は「確認待ち」に進むが、読み取れなかった入力を画面上に明示し、それが残っている間は確定できない。利用者はその入力を「除外」することで確定に進める。除外は「この入力は手作業で補う」という明示的な判断として扱う
  3. 読み取り不可の理由は4つ（判読不能／明細なし／タイムアウト／最大ターン数超過）。理由がタイムアウトまたは最大ターン数超過の場合に限り再実行できる。再実行は1回まで。再実行しても打ち切られた場合は再実行できなくなる。理由が判読不能または明細なしの場合は再実行しない（再実行しても結果が変わらない・明細は現れないため）
  4. 明細なしは、文字は読み取れたが、品目の明細と判断できる部分がどの入力にも見つからなかった場合（あいさつだけのメール本文、図面だけの PDF など）。明細を含まない入力が一部だけなら、その入力は「読み取り済み（明細なし）」とし、確定を止めない
- **例外・バリデーション**: 部分的に読めた場合も、読めた範囲を破棄せず提示する
- **受入基準**:
  - 次の4つの場合すべてで「読み取り不可」となり、理由が区別して表示される。いずれの場合も、そこまでに読めた範囲を破棄せず提示する
    - 判読不能（テキストレイヤのないスキャンPDF）
    - 明細なし（明細を含まないメール本文だけを投入）
    - タイムアウト（内側／外側のいずれか）
    - 最大ターン数超過
  - タイムアウトで打ち切られた案件は再実行でき、再実行後も打ち切られた場合は再実行できなくなる。判読不能・明細なしの案件には再実行の導線が出ない

### FUNC-08 営業担当による処理状況の確認

- **概要**: 営業担当が自分で処理状況を確認できる
- **事前条件**: 引合が投入されている
- **正常フロー**: 営業担当が、自分が転送した引合の現在の段階を確認する
- **例外・バリデーション**: 自分の担当外の引合は表示しない
- **受入基準**: 5段階すべてについて、営業担当が営業事務に問い合わせずに確認できる（KPI7）

### FUNC-09 顧客への問い合わせ文面の組み立て

- **概要**: 要確認の項目から、顧客に問い合わせる文面を組み立てて画面に表示する。送信はしない
- **事前条件**: 要確認の項目が1件以上ある
- **正常フロー**: 要確認の一覧から、品目・型番・不足している項目を並べた文面を生成して表示する
- **例外・バリデーション**: 要確認が0件のときは文面を生成しない
- **受入基準**: 要確認が3件以上ある案件で、3件すべてを含む文面が1通分生成される

### FUNC-12 認証（ログイン・ログアウト）

- **概要**: ユーザーIDとパスワードでログインし、営業事務ロールとして認証される
- **事前条件**: 利用者が登録されている
- **正常フロー**: 認証情報を入力する → 検証される → 引合一覧（SCR-02）へ遷移する
- **例外・バリデーション**: 認証に失敗したら理由を伏せて「ユーザーIDまたはパスワードが違います」。トークンの有効期限が切れたら再ログインを促す
- **受入基準**:
  - 正しい認証情報でログインでき、誤った認証情報では入れない
  - 有効期限切れの状態で操作すると、再ログインを促される
  - ログアウトすると認証が解除され、再ログインなしでは案件を操作できない
- **備考**: Foundation の Slice 0-4（JWT 認証）で実現する

## 3. スコープ

各機能を優先度で 4 区分に振り分ける。

| 区分                  | 意味                     |
| ------------------- | ---------------------- |
| **Scope 1（初版）**     | まず必ず作る。MVPとして成立させる最小機能 |
| **Scope 2（改善）**     | 初版の次に着手する改善・拡張機能       |
| **Scope 3（余裕があれば）** | 時間・リソースに余裕があれば実装する機能   |
| **Out of Scope**    | 今回は明確に実装しないと決めたもの      |

### Scope 1（初版）

| 機能ID    | 機能名              | 備考 |
| ------- | ---------------- | --- |
| FUNC-01 | 引合書の投入と形式判定    | これがないと始まらない |
| FUNC-02 | 引合内容の抽出        | エージェントの中核 |
| FUNC-03 | 処理状況の表示        | ジャーニー ステップ2 の受け皿 |
| FUNC-04 | 品目リスト案の確認      | HITL の本体。ここが価値の中心 |
| FUNC-05 | 値の修正と要確認項目の提示  | 確認とセット |
| FUNC-06 | 確定と品目リストの出力    | 完了条件そのもの |
| FUNC-07 | 読み取り不可の判定と引き渡し | 異常系の評価に必要 |
| FUNC-12 | 認証（ログイン・ログアウト） | Scope 1 の唯一のロール（営業事務）の入口。Slice 0-4 で実現する。**※ 製品としては Scope 1 のまま。ただし Sprint 3 では作っていない**（固定ユーザー `nakamura` で代替。理由は1章「Sprint 3 の実装範囲」） |

### Scope 2（改善）

| 機能ID    | 機能名            | 備考 |
| ------- | -------------- | --- |
| FUNC-08 | 営業担当による処理状況の確認 | 中村の作業は Scope1 で成立する。営業担当への展開は次段階。要確認を残して確定した案件が営業担当からどう見えるか（01 の持ち越し #1）は、Scope 2 の着手時に決める |

### Scope 3（余裕があれば）

| 機能ID | 機能名 | 備考 |
| --- | --- | --- |
| FUNC-09 | 顧客への問い合わせ文面の組み立て | 要確認の一覧があれば手動でも書ける |

### Out of Scope（今回は実装しない）

| 項目 | 実装しない理由 |
| --- | --- |
| 顧客から返事が来た後の往復（受領→修正→渡し直し） | 現在の運用（メールで受け取り、確定済みExcelを直接編集して渡し直す）のまま扱う。次の段階の課題 |
| スキャンPDF・手書きの判読 | 月に数件で優先度が低い。読み取り不可として人に引き渡す（FUNC-07）ことで実害を抑える |
| 顧客への問い合わせメールの送信 | 社外への送信は運用と責任の整理が必要。今回は文面をまとめるところまで |
| 顧客からの引合受信経路の変更 | 営業担当が営業事務へ転送する現行フローを変えない（要求定義 前提・制約5） |
| 顧客ごとの書式テンプレート登録機能 | 顧客に書式の統一を求めない（前提・制約2）方針と、初見の書式を扱えること（KPI4）を両立させるため、書式ごとの事前登録に頼らない設計とする |
| .xls（Excel 97-2003 形式）の受け付け | 教材が挙げている openpyxl は .xlsx 専用で .xls を読めない。別のライブラリが必要になり実装量に見合わない。届いた場合は「.xlsx で保存し直してください」と案内する（保存し直せば通常どおり処理できるため、手作業への切り替えは不要） |
| 読み取り不可の案件について、読めた範囲を土台に残りを手で入力すること | 読み取れなかった行はそもそも行として存在しないため、FUNC-06 の確定条件が判定できなくなる。中途半端に埋まったリストが購買へ流れるリスクもある |
| 同一の品目が複数のファイルに現れた場合の突き合わせ・重複排除 | どちらが正かの判断は業務知識を要する。今回は両方を行として並べ、人が確認画面で判断する。自動の名寄せは次の段階の課題 |
| FUNC-10 保持期間を過ぎたデータの自動削除 | すべてローカル実行で、評価期間は数日である。90日後の自動削除は今回の期間内に発火せず、動作を確認できない。保持期間の方針は非機能要件に定め、期限到来時の削除は当面手動運用とする。次の段階の課題 |
| FUNC-11 バックアップと復元 | ローカルの Docker ボリュームに閉じており、日常の起動・停止は営業事務の操作だけで完結する。この範囲では情報システム部門に手間が寄らないため、専用のバックアップ機能は今回作らない |

## 4. 非機能要件

| カテゴリ    | 要件 |
| ------- | --- |
| 性能      | ・1件の引合に投入できる入力は10件まで（ファイルとメール本文を合わせて数える）、合計50MBまで。1ファイルあたりの上限は20MB。入力の数はエージェントのターン数と API 費用に直結するため上限を設ける。メール本文も読み取りの対象なので、入力として数える<br>・平均12行の引合書1件について、投入から確認待ちになるまで3分以内。受入基準としてシステムテストの合否判定に使う<br>・エージェントは最大ターン数と2層のタイムアウト（内側 < 外側）で必ず打ち切る。ハングと暴走を防ぎ、API費用の上振れを抑える。タイムアウトの秒数と最大ターン数は agent.md で決める<br>・打ち切った場合も、そこまでの状態と読み取り元を破棄せず残す |
| セキュリティ（認証・認可方針） | 認証方式: JWT / トークン有効期限: アクセストークン 60分（ローカル実行のみのため長めに取らない） / 権限モデル: Scope 1 は営業事務ロールのみ（投入・確認・修正・確定）。購買担当はシステムを利用せず、出力された Excel をこれまでどおりの方法で受け取る。営業担当ロール（自分が転送した引合の状況確認のみ）は Scope 2 の FUNC-08 で追加する<br>・引合書は社外から預かった文書として扱う。保管場所をローカル内に限定し、閲覧できる範囲を上記ロールで制限する。保持期間: 確定した案件は確定日から90日。確定に至らなかった案件（読み取り不可のまま人に引き渡されたもの、確認待ちのまま放置されたもの）は投入日から90日。いずれも期限後に削除する（自動削除の実装は FUNC-10・今回は対象外）。90日は、見積の往復と、要確認の行が顧客回答待ちで残る期間を見込んだ値<br>・ANTHROPIC_API_KEY は backend/.env に置き、リポジトリに含めない |
| 可用性     | ・すべてローカル実行。クラウドへのデプロイはしないため、稼働率の目標は定めない<br>・処理中にエージェントが停止しても、引合の状態は失われず、再実行できる |
| ユーザビリティ | ・確認画面で「要確認」「確信が低い」「確信が高い」の3分類が一目で区別できる<br>・各値の読み取り元に1操作で辿れる（原本を探し直さない）<br>・未確認の行が残っている状態では確定できず、その理由が画面上で分かる<br>・営業担当の対応端末（スマートフォン対応の要否）は Scope2 の着手時に判断する |
