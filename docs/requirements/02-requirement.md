> Vモデル: 要件定義 / 対応する検証: システムテスト
> 要求定義（①）を「何を作るか」に翻訳する。各機能の要件・スコープ・非機能要件を定義する。

## 2. 各機能の要件

### FUNC-01 引合書の投入と形式判定

- **概要**: 引合書を受け取り、Excel / PDF / メール本文のどれとして読むかを判定して受け付ける
- **事前条件**: 営業担当から転送された引合メールを、営業事務が手元に持っている
- **正常フロー**:
  1. 営業事務がファイルを投入する（メール本文の場合は本文テキストを渡す）
  2. 形式を判定し、「Excel形式として受け付けました」のように何として読むかを表示する
  3. 受付済みの状態にして、抽出（FUNC-02）を開始する
- **例外・バリデーション**:
  - 対応しない拡張子は受け付けず、その場で理由を表示する
  - ファイルが破損して開けない場合は「読み取り不可」として FUNC-07 へ回す
  - サイズ上限（1ファイルあたり 20MB）を超える場合は受け付けない
- **受入基準**:
  - Excel添付・PDF添付・メール本文の3形式それぞれで、投入時に判定結果が表示される
  - 次の3つがそれぞれ拒否され、理由が表示される
    - 対応しない拡張子のファイル
    - 20MB を超えるファイル
    - 破損して開けないファイル（この場合は FUNC-07 の「読み取り不可」へ回る）

### FUNC-02 引合内容の抽出

- **概要**: 引合書から6項目（必須5項目と任意の備考）を行単位で抽出し、読み取り元と確信度を併せて記録する
- **事前条件**: FUNC-01 で受け付けが完了している
- **正常フロー**:
  1. 引合書を読み、明細の範囲を特定する
  2. 行ごとに 品目名・型番・数量・単位・納期・備考 を抽出する
  3. 各値について読み取り元を記録する
  4. 各値の確信度を判定し、読み違いの疑いがある値に「確信が低い」印を付ける
  5. 引合書に記載がない必須5項目（品目名・型番・数量・単位・納期）は「要確認」とする（空欄にしない）。任意項目の備考は、記載がなければ空欄のままとし、要確認にしない
- **例外・バリデーション**:
  - 小計行・合計行・注記行を明細として拾わない
  - 数量と単位が同じセルに書かれている場合は分離する（例「3箱(1箱50本)」）
  - 納期の表記ゆれ（「10月20日」「10/20」「10月末」「未定」）を、次の3つの値域のいずれかに正規化する。FUNC-05 の検査もこの値域に従う
    - (a) 確定日付 … 例 2026-10-20
    - (b) 月内の範囲 … 例「10月末」→ 2026-10-21〜2026-10-31 として保持し、範囲であることを明示する
    - (c) 要確認 … 「未定」や記載なしはここに入る
  - 判読できない場合は FUNC-07 へ回す
  - 最大ターン数・タイムアウトに達した場合は打ち切って状態を残し、「読み取り不可」として FUNC-07 へ回す
- **受入基準**:
  - 型番の桁違いと単位の取り違えを仕込んだ引合書で、該当行が「確信が低い」として示される（KPI8）
  - 納期または数量が欠けている引合書10件すべてで、確定前に欠落が提示される（KPI3）
  - 読み取り元 (1) 網羅性: 抽出したすべての値に読み取り元が付いている。欠けが0件
  - 読み取り元 (2) 正しさ: 3形式を各2件・計6件処理し、各件から無作為に5つの値を選んで読み取り元が指す場所を開き、実際にその値があることを確認する。計30値すべてが一致すること（一致率100%）。形式ごとの確認方法:
    - Excel … 指定されたシートのセル番地の値が、抽出値と一致する
    - PDF … 指定されたページに、抽出値の文字列が存在する
    - メール本文 … 指定された行番号に、抽出値の文字列が存在する
  - 次の2つが正しく処理される
    - 小計行・合計行・注記行を明細として拾わない（小計行を含む引合書で、抽出される行数が実品目数と一致する）
    - 数量と単位が同じセルに書かれている場合に分離できる（「3箱(1箱50本)」から 数量=3／単位=箱 を取り出す）

### FUNC-03 処理状況の表示

- **概要**: 引合1件の処理がいまどの段階かを表示する
- **事前条件**: FUNC-01 で受け付けが完了している
- **正常フロー**: 受付済み → 読み取り中 → 確認待ち → 確定済み の順に遷移し、各段階と残り時間の目安を表示する
- **例外・バリデーション**: 判読不能な場合、または処理が打ち切られた場合（タイムアウト・最大ターン数超過）は「読み取り不可」に遷移する。段階は5つのまま増やさない
- **受入基準**: 5段階すべてが画面上で区別でき、読み取り中は残り時間の目安が表示される

### FUNC-04 品目リスト案の確認

- **概要**: 抽出結果を3分類で表示し、読み取り元を確認しながら承認できるようにする
- **事前条件**: FUNC-02 の抽出が完了し、状態が「確認待ち」である
- **正常フロー**:
  1. 要確認の行と確信が低い行を先頭に寄せて表示する
  2. 営業事務がその行を1行ずつ確認する
  3. 確信が高い行が N 行あるとき、そのうち min(3, N) 行以上の読み取り元を開いたうえで、残りをまとめて確認済みにできる。読み取り元を1行も開いていない状態では一括確認できない
  4. すべての行が確認済み（未確認が0）になる
- **例外・バリデーション**:
  - 未確認の行が残っている間は確定できない
  - 抜き取りの最低行数に達していない場合、一括確認を実行させない
- **受入基準**:
  - 確認画面が表示されてから確定までが平均10分以内（連続10件の平均）（KPI1）
  - 3形式×2件の計6件を、ベテランに一度も聞かずに1件10分以内で確定できる。うち2件は初見の書式。誤りの見逃しは0件（KPI4）
  - 読み取り元を1行も開かずに一括確認しようとすると、実行できない
  - 読み取り元 (1): 確認画面上で、任意の値から1操作で読み取り元に辿れる
  - 読み取り元 (2): 読み取り元の表示形式が3形式それぞれで定義どおりである（Excel = シート名とセル番地／PDF = ページ番号と該当箇所／メール本文 = 行番号）

### FUNC-05 値の修正と要確認項目の提示

- **概要**: 誤った値を直し、顧客に問い合わせる項目を一覧にまとめる。顧客への問い合わせは、要確認の一覧をまとめた営業事務（中村）が、現行どおりメールで手作業で送る（送信は Out of Scope）
- **事前条件**: FUNC-04 の確認画面を開いている
- **正常フロー**:
  1. 誤って抽出された値を修正する
  2. 引合書に記載がない項目は「要確認」のまま残す
  3. 要確認の項目が一覧で提示され、1通の問い合わせにまとめられる
- **例外・バリデーション**: 修正後の値も形式の妥当性を検査する（数量は数値、納期は FUNC-02 の値域 (a)(b)(c) のいずれか）。(b) 月内の範囲 と (c) 要確認 は弾かない
- **受入基準**:
  - 要確認の項目が1画面にまとまって表示される
  - 納期の値が (a) 確定日付 (b) 月内の範囲 (c) 要確認 の3つのいずれかに分類されている。(a)(b)(c) のいずれでもない値は保存できない。「10月末」は (b) として月内の範囲を持ち、「未定」は (c) になる

### FUNC-06 確定と品目リストの出力

- **概要**: 内容を承認して確定し、品目リスト（Excel）を出力する
- **事前条件**: 未確認の行が0である
- **正常フロー**:
  1. 営業事務が確定を実行する
  2. 品目リスト（Excel）が出力される
  3. 要確認の行は「顧客回答待ち」と分かる形で出力に含まれる。出力された Excel は、これまでと同じ方法で購買部門に渡す（システム上での受け渡しはしない）
- **例外・バリデーション**: 未確認の行が残っている場合は確定させず「未確認の行があります」と表示する
- **受入基準**:
  - 全行に必須5項目が埋まり、引合書に記載がない項目は空欄ではなく「要確認」と明示される。区別のつかない空欄が1つでもあれば未達（KPI5）
  - 未確認の行が1行でも残っている状態では確定が実行できず、「未確認の行があります」と理由が表示される。未確認0のときのみ確定できる
  - 要確認の行を含む案件を確定したとき、出力された Excel 上でその行が「顧客回答待ち」と判別できる。要確認でない行と見分けがつくこと

### FUNC-07 読み取り不可の判定と引き渡し

- **概要**: 判読できない、または処理を打ち切った引合書を「読み取り不可」とし、理由（判読不能／タイムアウト／最大ターン数超過）を添えて人に引き渡す
- **事前条件**: FUNC-01 または FUNC-02 の途中で判読できないと判断された、または処理が打ち切られた（タイムアウト・最大ターン数超過）
- **正常フロー**: 状態を「読み取り不可」にし、理由と、どこまで読めてどこから読めなかったかを添えて人に引き渡す。段階は1つだが、中村が見る画面では理由を区別して表示する
- **例外・バリデーション**: 部分的に読めた場合も、読めた範囲を破棄せず提示する
- **受入基準**: 次の3つの場合すべてで「読み取り不可」となり、理由が区別して表示される。いずれの場合も、そこまでに読めた範囲を破棄せず提示する
  - 判読不能（テキストレイヤのないスキャンPDF）
  - タイムアウト（内側／外側のいずれか）
  - 最大ターン数超過

### FUNC-08 営業担当による処理状況の確認

- **概要**: 営業担当が自分で処理状況を確認できる
- **事前条件**: 引合が投入されている
- **正常フロー**: 営業担当が、自分が転送した引合の現在の段階を確認する
- **例外・バリデーション**: 自分の担当外の引合は表示しない
- **受入基準**: 5段階すべてについて、営業担当が営業事務に問い合わせずに確認できる（KPI7）

### FUNC-09 顧客への問い合わせ文面の組み立て

- **概要**: 要確認の項目から、顧客に問い合わせる文面を組み立てて画面に表示する。送信はしない
- **事前条件**: 要確認の項目が1件以上ある
- **正常フロー**: 要確認の一覧から、品目・型番・不足している項目を並べた文面を生成して表示する
- **例外・バリデーション**: 要確認が0件のときは文面を生成しない
- **受入基準**: 要確認が3件以上ある案件で、3件すべてを含む文面が1通分生成される

## 3. スコープ

各機能を優先度で 4 区分に振り分ける。

| 区分                  | 意味                     |
| ------------------- | ---------------------- |
| **Scope 1（初版）**     | まず必ず作る。MVPとして成立させる最小機能 |
| **Scope 2（改善）**     | 初版の次に着手する改善・拡張機能       |
| **Scope 3（余裕があれば）** | 時間・リソースに余裕があれば実装する機能   |
| **Out of Scope**    | 今回は明確に実装しないと決めたもの      |

### Scope 1（初版）

| 機能ID    | 機能名              | 備考 |
| ------- | ---------------- | --- |
| FUNC-01 | 引合書の投入と形式判定    | これがないと始まらない |
| FUNC-02 | 引合内容の抽出        | エージェントの中核 |
| FUNC-03 | 処理状況の表示        | ジャーニー ステップ2 の受け皿 |
| FUNC-04 | 品目リスト案の確認      | HITL の本体。ここが価値の中心 |
| FUNC-05 | 値の修正と要確認項目の提示  | 確認とセット |
| FUNC-06 | 確定と品目リストの出力    | 完了条件そのもの |
| FUNC-07 | 読み取り不可の判定と引き渡し | 異常系の評価に必要 |

### Scope 2（改善）

| 機能ID    | 機能名            | 備考 |
| ------- | -------------- | --- |
| FUNC-08 | 営業担当による処理状況の確認 | 中村の作業は Scope1 で成立する。営業担当への展開は次段階。要確認を残して確定した案件が営業担当からどう見えるか（01 の持ち越し #1）は、Scope 2 の着手時に決める |

### Scope 3（余裕があれば）

| 機能ID | 機能名 | 備考 |
| --- | --- | --- |
| FUNC-09 | 顧客への問い合わせ文面の組み立て | 要確認の一覧があれば手動でも書ける |

### Out of Scope（今回は実装しない）

| 項目 | 実装しない理由 |
| --- | --- |
| 顧客から返事が来た後の往復（受領→修正→渡し直し） | 現在の運用（メールで受け取り、確定済みExcelを直接編集して渡し直す）のまま扱う。次の段階の課題 |
| スキャンPDF・手書きの判読 | 月に数件で優先度が低い。読み取り不可として人に引き渡す（FUNC-07）ことで実害を抑える |
| 顧客への問い合わせメールの送信 | 社外への送信は運用と責任の整理が必要。今回は文面をまとめるところまで |
| 顧客からの引合受信経路の変更 | 営業担当が営業事務へ転送する現行フローを変えない（要求定義 前提・制約5） |
| 顧客ごとの書式テンプレート登録機能 | 顧客に書式の統一を求めない（前提・制約2）方針と、初見の書式を扱えること（KPI4）を両立させるため、書式ごとの事前登録に頼らない設計とする |
| FUNC-10 保持期間を過ぎたデータの自動削除 | すべてローカル実行で、評価期間は数日である。90日後の自動削除は今回の期間内に発火せず、動作を確認できない。保持期間の方針は非機能要件に定め、期限到来時の削除は当面手動運用とする。次の段階の課題 |
| FUNC-11 バックアップと復元 | ローカルの Docker ボリュームに閉じており、日常の起動・停止は営業事務の操作だけで完結する。この範囲では情報システム部門に手間が寄らないため、専用のバックアップ機能は今回作らない |

## 4. 非機能要件

| カテゴリ    | 要件 |
| ------- | --- |
| 性能      | ・平均12行の引合書1件について、投入から確認待ちになるまで3分以内。受入基準としてシステムテストの合否判定に使う<br>・エージェントは最大ターン数と2層のタイムアウト（内側 < 外側）で必ず打ち切る。ハングと暴走を防ぎ、API費用の上振れを抑える。タイムアウトの秒数と最大ターン数は agent.md で決める<br>・打ち切った場合も、そこまでの状態と読み取り元を破棄せず残す |
