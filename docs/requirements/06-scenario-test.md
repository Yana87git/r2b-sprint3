# シナリオテスト仕様書: 引合書整理エージェント

> Vモデル: システムテスト（右側）/ 対応する設計: ② 要件定義
> 5つの設計書（①〜⑤・`agent.md`）が固まった段階で、② の受入基準をもとに生成する。
> **Build した実アプリ**（モックではない）に対して手動で実行し、判定を記録する。

## 使い方（研修生向け）

1. Build した実アプリを起動する（前提環境を満たす）
2. シナリオを上から順に実行し、各ステップの期待結果と一致するか確認する
3. 判定欄に ☐Pass / ☐Fail を記録する（Fail はメモに事象を残す）
4. Fail は原因を **要件(②)・設計(③〜⑤・`agent.md`)・実装(Build)** のどこかに切り分けて修正する
5. 全シナリオ Pass ＝ 要件を満たしたことの証明

> **エージェントのシナリオ（TEST-03・05〜07・14〜18）は、トレース `backend/traces/{run_id}.jsonl` と突き合わせて判定する。** 観点は `agent.md` の完了条件・ツールの使い方・ガードレール・停止条件・秘密情報の5つ（3章）。

## 前提環境

| ---- | ---- |
| 対象 | Build した実アプリ（ローカル）。Frontend `http://localhost:3000` ／ Backend `http://localhost:8000` |
| 起動手順 | ターミナル1: `docker compose up -d`（PostgreSQL）／ ターミナル2: `cd backend && uv run uvicorn app.main:app --reload` ／ ターミナル3: `cd frontend && npm run dev` |
| 認証情報 | シーダーで作成した営業事務ロールの利用者（ユーザーID・パスワード）。ベテラン役は使わない（KPI4 は「ベテランに聞かずに」が条件） |
| テストデータ | `backend/tests/fixtures/` に置く（下表）。**実在の取引先の書類は使わない** |
| 初期状態 | 案件0件。`backend/traces/` は空。`backend/.env` に `ANTHROPIC_API_KEY` がある |
| 評価用の設定 | TEST-17・18 は停止条件を確かめるため、環境変数で `MAX_TURNS` / `INNER_TIMEOUT_S` を一時的に下げる（本番の値は `agent.md` の実行設定のとおり）。**TEST-19 #6 は「目安の時間を過ぎた」状態を作るため、残り時間の目安の係数 `ETA_BASE_S` / `ETA_PER_INPUT_S`（既定 30 秒 ／ 入力1件あたり 60 秒）を一時的に下げる。** いずれも backend の起動時に環境変数で渡し、**確認後は必ず既定値に戻す**（下げたままだと他のシナリオの表示が変わる） |

> **期待結果に数字を書くときの約束（2026-09-13）**
>
> 件数・行数のような**テストデータから決まる数字は、期待結果にベタ書きしない**。
> 上の「用意するテストデータ」や `backend/tests/fixtures/README.md` の正解表から導ける表現にする
> （例: 「D2 の全件」「D3 の欠落一覧に定義したすべての箇所」「投入した Excel の明細行数と一致する行数」）。
> データを差し替えたときに、期待値だけが古いまま残るのを防ぐため。
> 一方、**仕様として決まっている数字はそのまま書く**（1ファイル 20MB・最大10ファイル・合計 50MB・
> 抜き取り min(3, N)・投入から確認待ちまで3分以内・1件10分以内・トークンの有効期限60分）。
