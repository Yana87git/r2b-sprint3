# C4 の3階層で、自分のコードを説明する（Review フェーズ・質疑対策）

`/r2b-review-sprint3` のガイドを通す前後で使う下敷き。**設計書ではなく、実コードを読んで書いた**。
発表の質疑（6〜7分）で聞かれるのは、ほぼこの3階層のどれか。

---

## L1 全体像 ── 何を自動化し、何を人に残したか

### 境界の外にあるもの

| 外部 | 中身 |
|---|---|
| 入力 | 顧客から届く引合書類（Excel・PDF・Word・メール本文）。**顧客ごとに書式が違い、統一は求められない** |
| 外部サービス | **Claude API のみ**（`claude-agent-sdk` 経由）。他に外部通信はしない |
| 出力 | 品目リストの Excel。購買担当はシステムを使わず、これまでどおり Excel を受け取る |
| 利用者 | 営業事務1名（中村）。Sprint 3 では認証を実装せず**固定ユーザー**で動かす |

### なぜルールベースではなくエージェントか

書式が統一されないので、ルールベースだと**書式ごとに実装が要る**。新規顧客の見慣れない書式は
ベテラン1名に聞くしかない、という属人化がそのまま課題だった。

そこで**判断だけを LLM に任せ、手順はコードで書いた**。

| LLM の判断 | 通常のコード |
|---|---|
| 明細がどこにあるか（シート・表・ページ・本文） | 形式の判定（拡張子で決まる） |
| 列や項目の意味（「型式」「品番」→ 型番） | 中身を位置つきで取り出す |
| 小計・合計・注記の行を明細から外す | 読み取り元の位置に原文があるかの照合 |
| 読み違いの疑いがある値に印を付ける | **完了条件の判定** |

### 人に残したもの

**確定・除外・Excel 出力・顧客への連絡。**エージェントが作るのは「確定前の案」だけで、
**確定する手段そのものを与えていない**（ツールが6つしかない）。

> 「機械が出したから正しい、という運用にはしたくない」── ベテラン営業事務の言葉を
> 前提に置いた。全自動にしないことが設計の出発点。

## L2 地図 ── どこに何があるか

### プロセスは3つ（すべてローカル）

```
Next.js 15 (:3000)  ──HTTP──▶  FastAPI / uvicorn  ──▶  PostgreSQL (Docker)
                                      │
                                      └──▶ Claude API（claude-agent-sdk）
```

### backend の層（依存は外→内の一方向）

```
api/v1/endpoints/  ──▶  services/  ──▶  repositories/ + models/
                          │
                          └──▶ agent/     ← Business Logic に属する
```

- エンドポイントは `inquiries.py` に16、`runs.py` に1
- `services/` は18本。案件受付・品目下書き・確認・修正・除外・確定・出力・再実行などが1本ずつ
- **エージェント実行は `app/agent/` に閉じ込め、起動は service 層から `jobs.start_agent_job()` で行う**

### `app/agent/` の7ファイル

| ファイル | 役割 |
|---|---|
| `definition.py` | モデル・最大ターン数・タイムアウト3種。`agent.md` の写し |
| `prompt.py` | システムプロンプト（128行）。`{inquiry_id}` だけ実行時に埋める |
| `tools.py` | **6つのツール**と `ALLOWED_TOOL_NAMES`。in-process MCP サーバとして登録 |
| `runner.py` | 実行ループ。**内側**のタイムアウト（無応答・全体）と最大ターン数 |
| `jobs.py` | バックグラウンドジョブ。**外側**のタイムアウト（`asyncio.wait_for`） |
| `trace.py` | JSONL レコーダー（`backend/traces/{run_id}.jsonl`） |
| `context.py` | 案件IDの注入（LLM からは指定できない） |

### 6つのツール

`list_input_files` / `read_file_content` / `save_item_rows` / `verify_sources` /
`set_file_status` / `check_completion`

組み込みツール（Bash・Read・Write・Glob・Grep・WebFetch・WebSearch・Task・ToolSearch）は
`disallowed_tools` で**呼べなくしてある**。プロンプトのお願いではなく設定で塞いでいる。

### テーブル8つ

`users` / `inquiries` / `inquiry_inputs` / `item_rows` / `item_values` /
`value_clues` / `agent_runs` / `item_list_exports`

- 値は行ではなく **`item_values` に1つずつ**持つ（原文・正規化した値・状態・確信度・読み取り元）
- 確信が低い理由は `value_clues`（H1〜H4）に別テーブルで持つ
- 除外は `excluded_at` を立てるだけで、`confirmed_at` は触らない（取り消しで元の状態に戻る）

### frontend

`features/{inquiries, items, runs}` の3つ。各 feature が `api.ts` / `hooks.ts` /
`components/` を持ち、`index.ts` 経由でのみ他から参照される。
画面は7つ（一覧・投入・処理状況・品目リスト案・確定済み・読み取り不可・実行状況）。
`page.tsx` は8つあるが、残る1つは `/` から一覧へのリダイレクト。

## L3 流れ ── 1件の引合書が、投入から確定までどう動くか

```
① POST /inquiries                      202 + run_id を即返す（完了を待たない）
     └ 案件と入力を作り、そのままエージェントを起動する
②   jobs.start_agent_job()             asyncio.create_task で裏に回す
③     asyncio.wait_for(OUTER_TIMEOUT)  ← 外側。内側が機能しなかったときの最後の砦
④       runner.run_agent()             ← 内側。無応答60秒 / 全体300秒 / 最大30ターン
⑤         エージェントのループ
             list_input_files
             read_file_content   ← 1回の手番で1つの入力だけ
             save_item_rows      ← 入力を1つ読み終えるごとに（打ち切られても残すため）
             （繰り返し）
             verify_sources      ← 読み取り元の位置に原文があるか照合
             check_completion    ← 完了条件①〜⑥を機械的に判定
⑥   トレースに result を書く            stop_reason = completed / failed /
                                        max_turns / inactivity_timeout /
                                        inner_timeout / outer_timeout
────────────────────────────── ここから人 ──────────────────────────────
⑦ GET /runs/{run_id} をポーリング       refetchInterval。進捗はトレースの末尾
⑧ 品目リスト案を確認                    行ごとの確認 / まとめて確認（抜き取り min(3,N)）
                                        値の修正・行の除外・入力の除外
⑨ POST /confirm                        未確認0 かつ 読み取れなかった入力0 のときだけ通る
     └ Excel を生成し、item_list_exports に記録。案件を「確定済み」に
```

### 押さえておくと答えやすい3点

**1. なぜ HTTP で完了を待たないのか**
読み取りは数十秒〜3分かかる。同期で待つとタイムアウトとリトライの設計が HTTP 側に漏れる。
**POST → 202 + run_id → GET でポーリング**を実行の型にし、進捗はトレースの末尾をそのまま返す。

**2. 完了は誰が決めるのか**
**`check_completion`（コード）**。LLM の自己申告では完了にしない。6条件のうち1つでも欠ければ
「未達」と、どの条件が欠けているかを返し、エージェントは直して呼び直す。
`runner.py` は、`check_completion` が失敗を返したとき `completed` を `failed` に**上書きする**。

**3. 止まり方が6通りある**
`completed`（確認待ち）/ `failed`（全入力が読み取り不可・明細0行 → 読み取り不可）/
`max_turns`・各種 `timeout`（読み取り不可・**再実行が1回だけできる**）。
**画面はこの `stop_reason` だけを見て、再実行の導線を出すかどうかを決めている。**

## 質疑で聞かれそうなことと、答えの在り処

| 問い | 答えの在り処 |
|---|---|
| なぜ全自動にしないのか | L1「人に残したもの」。ツールを6つしか与えていない |
| LLM が嘘をついたらどうするのか | `verify_sources` で原文と照合。不一致が0件でないと完了しない |
| 完了したと言い張ったら | `check_completion` が機械的に判定。自己申告では完了にしない |
| ハングしたら | タイムアウト2層。外側（`jobs.py`）が必ず回収する |
| 「確信が低い」と「要確認」は何が違うのか | 読み取りの状態 と データの状態。確定を止めるのは「未確認」だけ |
| どれくらい速くなるのか | 1件30分 → 平均1.7分（8件・開発者本人の計測なので下限の目安） |
| 誤りを見逃さないのか | 仕込んだ8件を 8/8 検知、確定後の残存 0/8 |
| テストはどこまで書いたのか | ツール（決定的関数）は単体テスト。**エージェントループは書かない**（非決定的）。代わりに評価シナリオ19本とトレース検証 |
| 本番で動くのか | 動かしていない。ローカル実行のみ。認証（ログイン画面）は未実装。営業担当の画面と自動削除は Scope 2 のため対象外 |
