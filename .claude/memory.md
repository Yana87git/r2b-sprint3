## 1. アーキテクチャ決定 (ADR-lite)

- [AD-001] 実行の型は「POST → 202 + run_id → GET ポーリング」。HTTP で完了を同期待ちしない。
  理由: 読み取りは2〜3分かかり、リクエストの寿命より長い / 影響範囲: ⑤ #4・#8、SCR-04
- [AD-002] タイムアウトは2層 + 無応答検知（無応答60 < 内側300 < 外側360）。
  評価のときだけ環境変数で下げ、**明示しなかった側は大小関係を保つよう自動で寄せる**。
  理由: 外側が先に発火すると停止理由が失われる / 影響範囲: `definition.py`・`runner.py`・`jobs.py`
- [AD-003] 停止理由（`stop_reason`）は agent.md の6種に固定し、案件の「読み取り不可」の理由に対応づける。
  **理由の付いていない `failed`（予期しない例外）でも案件を必ず読み取り不可にする**。
  理由: 付けないと案件が「読み取り中」のまま残り、一覧が永久に読み取り中に見える / 影響範囲: `agent_run_service.finish_run`
- [AD-004] 確定を止める規則は**1つだけ**（未確認0 かつ 読み取れなかった入力0件）。経路で変えない。
  理由: 経路ごとに規則を分けると経路ごとに穴が開く / 影響範囲: SCR-05・⑤ #17
- [AD-005] 確信が高い行を確認できる条件（読み取り元を開いた / 抜き取りが min(3,N)）は
  **個別確認と一括確認の両方でサーバーが判定する**。画面だけに頼らない / 影響範囲: ⑤ #11・#12
- [AD-006] 認証（FUNC-12）は Sprint 3 では作らず、固定ユーザー `nakamura` で動かす。
  製品スコープ（Scope 1）からは外さず、**実装範囲を別表に書き分ける** / 影響範囲: ② 1章・⑥ TEST-01・02
- [AD-007] エージェントに公開するツールは agent.md の6つだけ。疎通用 `ping` は削除した（2026-09-17）。
  理由: プロンプトの文章だけで塞ぐのは「お願い」であり、§5 のガードレール原則に反する / 影響範囲: `tools.py`

## 2. 確立した規約・パターン

- [CV-001] **設計書と実装が食い違ったら、先に設計書を引用して「どちらが誤りか」を判定する。**
  判定せずに期待値を実装に合わせない。判定は `/design-check`（答えは 実装の誤り／設計の誤り／
  規定が無い／読み違い の4つ）。§4 の RV-001・RV-002 から昇格
- [CV-002] 規則は**経路ごとに分けない**。画面とサーバー、個別と一括で別々の判定を書かない。§4 RV-003 から昇格
- [CV-003] テストの期待結果に固定の数字を書かない。**テストデータの定義から導く形**で書く
  （例:「投入した Excel の明細行数 ＋ PDF の追加品目」）
- [CV-004] **根拠が確認できないものを Pass にしない。** ⑥ の判定欄は
  ☑Pass / ☒Fail / ⚠一部 / ☐未実施 / ☐対象外 を使い分け、Pass には日付と確認方法を書く
- [CV-005] 規則をプロンプトに書くときは**理由を添える**。抽象的な指示だけでは守られない（LN-002）
- [CV-006] エージェントに守らせたい規則のうち、**機械で判定できるものは仕組みで止める**
  （hooks / スクリプト）。意味を読む必要があるものは skill にして呼べるようにする

- [RV-003] 抜き取りの規則が一括確認にしか効いておらず、個別のチェックボックスから素通りできた。
  → サーバー側（⑤ #11）にも同じ判定を入れた。同じ構造で確定の規則も経路ごとに2通りになっていた → CV-002 へ昇格

  → 実装を修正。あわせて理由なしの `failed` で案件が「読み取り中」のまま残る穴も塞いだ（AD-003）

## 5. 学び・ハマりどころ（再発防止）

- [LN-001] **「テストが通った」はエージェントの保証ではない。** 停止条件のバグ3件は、
  評価用に `MAX_TURNS=3` に下げて**実際に打ち切らせて**初めて出た。
  検査も同じで、「動いた」ではなく**「止まるべきときに止まった」**を確かめる
- [LN-002] **規則をプロンプトに書くだけでは守られない。** 「入力を1つ読み終えるごとに保存」は、
  複数入力の実行32本のうち31本で守られていなかった。理由を添えて書き直しても半分しか直らず、
  **「1回の手番で2つの入力を同時に読まない」と並列呼び出し自体を禁じて**初めて守られた。
  → 順番が意味を持つ規則は、並列に呼べること自体を止めないと効かない（本来はツール側で強制するのが確実）
- [LN-003] **rule に書いてあっても、その場面だと気づけなければ発火しない。**
  「設計が正」（`agent-development.md` §1）は前からあったのに、食い違いの場面で2回とも発火しなかった。
  → 気づく機会を機械側に持たせる（spec-sync が `/design-check` を名指しする）
- [LN-004] 中断した実行はトレースに `run_end` を書けない（プロセスが死ぬため）。
  起動時の回収が **DB だけ**を閉じていて、停止理由の無いトレースが残っていた。
  → 回収時にトレースにも `run_end` を書く。**記録されない実行は評価できない**
- [LN-005] `--reload` で動かしているサーバーは、実行中にファイルを保存すると**再起動して実行が消える**。
  評価の測定中はリロード無しで起動する
- [LN-006] 計測の窓に注意。KPI4 の1件が13分になったのは、最初に開いて最後に確定したため
  （`review_started_at` → `confirmed_at` が他の7件を含んでいた）。1件ずつ開いて閉じる
