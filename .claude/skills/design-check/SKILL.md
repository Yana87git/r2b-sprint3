# Purpose

実装と設計書が食い違ったとき、**どちらが誤りかを先に判定する**。

既定の動きは「設計書のほうが間違っていることにして、期待値を実装に合わせる」になりやすい。
2026-09-13 に2回起きた。うち1件は `agent.md` を引いて止めなければ、**実装のバグが「仕様どおり」として
⑥ に記録される**ところだった。

`.claude/rules/agent-development.md` §1「設計が正」は前から書いてある。それでも発火しなかったのは、
その場面で「いまが §1 の場面だ」と気づけないため。判定には**日本語の散文を読む**作業が要るので
hooks では止められない。だから skill にしてある。

# When to use

- 実装の挙動と設計書（01〜06・`agent.md`）の記述が食い違ったとき
- テストが落ちて、「期待値のほうを直そうか」と考えたとき（**そう考えた時点でここに来る**）
- `spec-sync.mjs` が「実装にあるが agent.md に無い / agent.md にあるが実装に無い」で止めたとき
- レビューで「設計と実装の食い違い」を指摘されたとき

# 起動

```
/design-check <食い違いの内容を1文で>
```

例: `/design-check 判読不能のときの stop_reason が completed になっている`

# 手順（順番を変えない）

**1. 食い違いを1文で書く**
「何が、どう食い違っているか」だけ。原因も対策もまだ書かない。

**2. 設計書を先に引く**（実装を見る前に）
ファイル名と行番号つきで、**原文のまま**引用する。要約しない。
探す順番は **02-requirement.md → agent.md → 03-spec.md → 04-db.md → 05-api-ipo.md → 06-scenario-test.md**。
要求（何を満たすべきか）から見て、詳細に降りる。
**行番号は設計書を編集するとずれる。** 引用するときは毎回 `grep -n` で取り直す（下の実例の行番号も同じ）。

```bash
grep -n "<キーワード>" docs/requirements/02-requirement.md docs/requirements/agent.md \
  docs/requirements/03-spec.md docs/requirements/04-db.md docs/requirements/05-api-ipo.md \
  docs/requirements/06-scenario-test.md
```

**3. 引けなかったら「設計に規定が無い」と結論する**
これは第3の答えであって、負けではない。**推測で埋めない。**
「たぶんこういう意図だろう」と書いた時点で、設計書に無いものを設計ということにしている。

**4. 実装の該当箇所を引く**
ファイル名と行番号つき。こちらも原文のまま。

**5. 判定する**（答えは4つのどれか）

| 判定 | 意味 | すること |
|------|------|---------|
| **実装の誤り** | 設計書に規定があり、実装がそれと違う | 実装を直す。**設計書は変えない** |
| **設計の誤り** | 設計書の記述自体が誤り（書き損じ・古い理由・他の記述と矛盾） | **設計書を先に直してから**実装を直す |
| **規定が無い** | 設計書のどこにも書かれていない | **人に上げる。勝手に決めない** |
| **読み違い** | 実際には食い違っていない | 何も直さず、なぜそう見えたかを記録する |

**6. 判定の根拠を残す**
下の出力テンプレートの形で、引用つきで残す。残す先は場面による
（⑥ の実施者メモ／設計書の訂正注記／`.claude/memory.md` §4・§5）。

**7. 直す**
「実装の誤り」なら実装だけ、「設計の誤り」なら設計書 → 実装の順。
「規定が無い」なら**ここで止めて人に渡す**。

# してはいけないこと

- **テストの期待値を実装の挙動に合わせて書き換えて、食い違いを消すこと**
  （実装のバグが「仕様どおり」になる。2026-09-13 に踏んだ）
- **設計書を読まずに、実装の挙動から設計の意図を推測すること**
- **「たぶんこういう意図」と書くこと**。引用できないなら答えは「規定が無い」
- 判定の前に直し始めること（手順2〜5 を飛ばさない）

# 出力テンプレート

```markdown
## 食い違い
<1文>

## 設計書の記述
`<ファイル>:<行>`
> <原文のまま引用>

（引けなかった場合は「02〜06・agent.md を <キーワード> で検索したが規定なし」と書く）

## 実装
`<ファイル>:<行>`
> <原文のまま引用>

## 判定
実装の誤り / 設計の誤り / 規定が無い / 読み違い
理由: <設計書の記述と実装のどこがどう違うか>

## 直し方
<何をどの順で直すか。「規定が無い」なら「人に上げる。決めてほしいのは〜」>
```

# 実例（結論が逆になる2つ。両方を読むこと）

片方だけを覚えると「いつも実装が悪い」という誤った型になる。**判定は毎回やる。**

## 例1 判定＝実装の誤り（2026-09-13・TEST-15 #5 / TEST-16 #4）

```markdown
## 食い違い
判読不能（D4）・明細なし（D5）で終わった実行の `stop_reason` が、トレースでは `completed` になっている。

## 設計書の記述
`docs/requirements/agent.md:82`
> | 失敗（中断） | (1) 投入した全入力が読み取り不可 (2) 読み取れた入力の明細が合計0行（明細を含まない
> 書類・本文だけが投入された） | `check_completion` が入力の状態と行数から判定し、案件を「読み取り不可」に
> する。理由は (1) 判読不能 (2) 明細なし。`stop_reason` は `failed` |

`docs/requirements/agent.md:92-93`（停止理由と ② FUNC-07・③ SCR-10 の理由の対応）
> | `failed`（全入力が読み取り不可） | 読み取り不可 | 判読不能 | できない |
> | `failed`（明細が0行） | 読み取り不可 | 明細なし | できない |

## 実装
`backend/app/agent/runner.py`（当時）
> `result.stop_reason = "completed" if not message.is_error else "failed"`
> — `check_completion` が `failed_illegible` を返しても、SDK 側が正常終了なら completed になる

## 判定
実装の誤り。設計書は `failed` と明記しており、SCR-10 の再実行の可否もこれで決まる。

## 直し方
実装を直す（ContextVar で `check_completion` の結果を runner に渡し、`failed_*` なら
`stop_reason=failed` にする）。設計書は変えない。D4・D5 を流し直して再判定する。
```

## 例2 判定＝設計の誤り（2026-09-13・TEST-03 #4）

```markdown
## 食い違い
D1 の抽出結果が13行だが、⑥ の期待結果は「12行」になっている。

## 設計書の記述
`docs/requirements/06-scenario-test.md:32`（用意するテストデータ）
> | D1 | `normal_excel.xlsx` ＋ `normal_spec.pdf` | 明細12行・小計行あり・「3箱(1箱50本)」・
> 「10月末」。PDF は追加品目1と材質の補足 | TEST-03・08〜13 |

## 実装
D1 を流した結果は13行（Excel の12行 ＋ PDF の追加品目1行）。
`backend/app/agent/prompt.py`「複数の入力があるとき」
> - 片方の入力にしかない品目も、行として加えます

## 判定
設計の誤り（期待値の書き損じ）。テストデータの定義（12 ＋ 1）から13行が正しく、
実装もプロンプトの規定どおりに動いている。

## 直し方
⑥ の期待結果を「**投入した Excel の明細行数 ＋ PDF の追加品目**（D1 なら13行）」に直してから
再判定する。実装は変えない。
（あわせて、期待結果に固定の数字を書かずテストデータ定義から導く形に直す）
```

# 確かめ方（答えの分かっている問いを投げる）

このスキルが効いているかは、次の3つで確かめる。**3が一番大事。**

1. 「判読不能なのに `stop_reason` が completed」→ `agent.md:82` を引いて**実装の誤り**と判定するか
2. 「D1 の抽出が13行だが期待値は12行」→ D1 の定義を引いて**設計の誤り**と判定するか
3. 「`read_file_content` の `limit` の上限値が実装では N だが、設計書に数値が無い」
   → 勝手に決めず、**「規定が無い。人に上げる」**と答えるか

3 で数値を決めてしまったら、このスキルの書き方が悪い。**「分からない」と言えないスキルは、
いちばん危険な場面で嘘をつく。**
